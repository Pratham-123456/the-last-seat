# Database Design Reference

Schema source of truth: [`migrations/versions/0001_initial_schema.py`](../migrations/versions/0001_initial_schema.py). ORM mirror: [`app/models/__init__.py`](../app/models/__init__.py). Diagram: [erd.md](erd.md).

## Design principles

1. **Inventory is immutable, state is append-only.** `seats` never changes after seeding. Reservation and payment rows change status but are **never deleted**, so the full history of every seat is auditable (`EXPIRED`/`CANCELLED` rows stay forever).
2. **Availability is derived, not stored.** There is no `seats.is_available`. A boolean copy would have to be kept in sync with `reservations.status` and with the clock (a hold silently "becomes" free at `expires_at`) — two sources of truth that can disagree. Instead availability is computed by a join at read time.
3. **The database enforces the rules.** CHECK constraints make illegal states unrepresentable; partial unique indexes make double booking and double charging impossible even if application code is wrong.
4. **All time is `TIMESTAMPTZ` in UTC**, and decision timestamps come from PostgreSQL's `clock_timestamp()`, never the API server's clock (several API servers could disagree by a few ms).

## Indexes and the queries they serve

| Index | Definition | Serves |
|---|---|---|
| `uq_reservations_one_active_per_seat` | `UNIQUE (seat_id) WHERE status IN ('HELD','CONFIRMED')` | integrity; also the "active hold for this seat?" lookup |
| `ix_reservations_seat_status` | `(seat_id, status)` | lazy-expiry `UPDATE` and the seat-availability join |
| `ix_reservations_expiry_scan` | `(status, expires_at) WHERE status='HELD'` | expiry worker candidate scan — tiny, because only live holds are indexed |
| `ix_reservations_customer_created` | `(customer_ref, created_at DESC)` | `GET /customers/{ref}/bookings` newest-first |
| `ix_reservations_event_status` | `(event_id, status)` | per-event summaries |
| `uq_payment_one_succeeded_charge_per_reservation` | `UNIQUE (reservation_id) WHERE payment_type='CHARGE' AND status='SUCCEEDED'` | integrity: no double charge |
| `ix_payment_attempts_reservation_created` | `(reservation_id, created_at DESC)` | payment history per reservation |
| `uq_payment_attempts_reservation_id_attempt_number` | `UNIQUE` | attempt numbering |
| `uq_seats_event_id_seat_number` | `UNIQUE` | seat lookup by number (the `FOR UPDATE` query) |

## The derived-availability query

```sql
SELECT s.id AS seat_id, s.seat_number, r.status AS r_status, r.expires_at
FROM seats s
LEFT JOIN reservations r
       ON r.seat_id = s.id
      AND (r.status = 'CONFIRMED' OR (r.status = 'HELD' AND r.expires_at > :t_now))
WHERE s.event_id = :event_id
ORDER BY s.seat_number;
```

No match → `AVAILABLE`; matched `HELD` → `HELD` (with `held_until`); matched `CONFIRMED` → `CONFIRMED`. Because of the partial unique index the join produces at most one row per seat. A stale `HELD` row (past `expires_at`, not yet rewritten) is excluded by the `expires_at > :t_now` condition, so readers never see a phantom-held seat.

## Migrations

```powershell
.\.venv\Scripts\alembic.exe upgrade head      # apply (additive)
.\.venv\Scripts\alembic.exe current           # show applied revision
.\.venv\Scripts\alembic.exe history           # list revisions
```

`migrations/env.py` reads the URL from `DATABASE_URL` and **refuses any database other than `last_seat_db` / `last_seat_test_db`** (it prints the target before running). `alembic downgrade` drops all project tables — it is destructive and should only be run deliberately.

To change the schema: edit the models, create `alembic revision -m "describe change"`, write `upgrade()`/`downgrade()` by hand (prefer additive changes), run against `last_seat_test_db` via the test suite first.
